## Problem

CI run 37061505863 (commit e2d35ff, 2026-10-02) failed only on 7 live web-search tests. Brave sent `HTTP 429` ("braveHTML: blocked (HTTP 429)") and DuckDuckGo sent a challenge page to the runner `mini`. The code recognized both as a block of the provider. The tests still failed:

- `DuckDuckGoHTMLLiveTests` and `BraveHTMLLiveTests` ("the Swift query gives at least 3 https hits...", "a site search for developer.apple.com..."): each recorded a known issue for the block, and then also failed (2 issues, 1 known).
- `KeyedFallbackLiveTests` ("a braveAPI key that is not valid gives the refused-key note..."): the refused key (`HTTP 422`) worked as designed, then the keyless fallback was blocked, and 4 expectations failed (`result.correction == nil`, `result.provider == keylessProvider.name`, the hit count, the refused-key note).
- `KeylessChainLiveTests` ("the keyless chain gives hits..."): both keyless providers were blocked; 3 expectations failed.
- `WebRunCodeLiveTests` ("the goal snippet returns 1 to 3 pages..."): the search gave `[]`, the snippet returned `[]`, and the uncarried-return notice was added after the JSON output, so the test could not decode the output.

## Decision of the user (2026-10-02)

"If the provider blocks, we managed to talk to it, didn't we."

Thus a block that the code recognizes (an `HTTP 429`, or a challenge page) proves that the request reached the provider. That is a pass for the reach of the provider. A live test cannot make a provider that blocks the runner give results.

## Rule for each live web test

Each live web test passes on exactly one of these two outcomes, and fails on any other:

1. **Results.** The provider gave results, and the test checks them as it does now (hit count, https, the expected site, and so on).
2. **A recognized block.** The provider answered with a response that the code classifies as a block (`HTTP 429`, or a challenge page). The test then checks what the code controls: the block is reported with the provider name and the kind of block (in the correction or the note, in the form the code writes now), the result holds no invented hits, and a chain goes on to the next provider as designed.

Any other outcome fails: a transport error, a timeout, a response the code cannot parse, an unclassified HTTP status, or a block that the code does not report.

The checks for the refused key in `KeyedFallbackLiveTests` (the `HTTP 422` refused-key note) stay mandatory in both outcomes, because the key is refused by design.

`WebRunCodeLiveTests`: when the search is blocked, the test must check the block report that the snippet output carries, and must not try to decode the output as pages. Examine also whether the uncarried-return notice after a JSON value that a snippet returned on purpose (an empty array from an empty search) is correct; if it is a defect of this package, fix it with a unit test.

## Constraints

- Do not skip a test, and do not use `withKnownIssue` (or any other known-issue mark) to hide a failure. A recognized block is a pass with checks, not a known issue. Remove the known-issue handling that commit `36ffe02` added, and replace it with the rule above.
- Do not widen a deadline or add a retry. Do not add a fixed model-quality score. Do not repeat a test.
- Every live web test still runs on each push, in the same integration job.
- Put the rule in one shared helper, so that each test uses the same two outcomes.
