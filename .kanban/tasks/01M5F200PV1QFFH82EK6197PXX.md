## What
Per EXTRAS-7 / D82 (TestudoApp `features/packages/foundationmodels-extras.md`), the top-level `MultiTool` tool (`runCode`) conforms to `GraphQLEndpointTool` and gives the endpoints of its capabilities. APP-16 reads endpoints only from the top-level tool list, so this is the **only** way the app finds `snapshots` (MT-13), `files` (MT-11) and `settings` (ACPA-17 mounts `SettingsTool` with `withOperationTool`, not as a top-level tool).

`MultiTool.Registry` keeps no capabilities: `buildRegistry()` in `Sources/FoundationModelsMultitool/Surface/RegistrySource.swift` flattens them into verb tools. So the endpoints are collected while the registry is built:
- `Sources/FoundationModelsMultitool/Surface/Capability.swift`: add `var graphQLEndpoints: [any GraphQLEndpoint] { get }` to `Capability`, with a protocol-extension default that collects the endpoints of `tools` cast to `GraphQLEndpointTool`.
- `Sources/FoundationModelsMultitool/Surface/OperationToolCapability.swift`: override it to return `(tool as? any GraphQLEndpointTool)?.graphQLEndpoints ?? []`. `tools` there is `[tool]`, but the registry expands it into `OperationVerbTool` verbs.
- `Sources/FoundationModelsMultitool/Surface/RegistrySource.swift`: `buildRegistry()` collects each capability's endpoints in capability order before expansion, removes repeats by `(name, scope)` keeping the first (the D77 rule of the host), and stores them on a new `Registry.graphQLEndpoints` field. It is a new `Registry` init parameter with default `[]`; update every place that builds `Registry` directly (grep for `Registry(`).
- `Sources/FoundationModelsMultitool/MultiTool.swift:325`: `MultiTool: GraphQLEndpointTool`; `graphQLEndpoints` returns the endpoints of the current registry, so an MCP registry swap is reflected.

Files: `Capability.swift`, `OperationToolCapability.swift`, `RegistrySource.swift`, `MultiTool.swift`, and the test file. Conventions: EXTRAS-9 (TestudoApp `features/packages/foundationmodels-extras.md`, D115).
