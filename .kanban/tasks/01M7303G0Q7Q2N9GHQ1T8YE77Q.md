## What
D128 (d), MT-15: in `sandboxed` mode the stdio MCP servers (`StdioServerProcess`) are not registered. The HTTP MCP servers stay.

Research fact: Multitool does not start the stdio servers. The host starts them before the builder: ACPAgent `Tools/MCPComposition.swift` (`connectServers`) makes each `StdioServerProcess`, connects an `MCPServer` over it, and then gives the connected servers to `MultiTool.Builder.withMCP(servers:)` (`Surface/MultiToolBuilder+Capabilities.swift:295`). Thus the builder sees an `MCPServer`, not the transport. The host (ACPA-19) must not start a stdio server in `sandboxed` mode. Multitool adds a second, hard guard:

- `Capabilities/MCP/StdioServerProcess.swift`: the start of the process takes the `ToolMode` (or reads it from a new parameter of `StdioServerProcess.init`) and throws a new `StdioServerProcessError.notAvailable(mode:)` in `sandboxed` mode BEFORE `posix_spawn`. This error is a `NonRetryableConnectError` (see the extension near line 576), so a connect does not retry it.
- `Capabilities/MCP/MCPServer+Connection.swift`: `MCPServer` records that its transport is a child process when the transport comes from `StdioServerProcess` (for example a marker protocol on that transport type, `ChildProcessTransport`). `withMCP(servers:)` in `sandboxed` mode makes `buildRegistry()` throw the `notAvailable` error of the builder task for such a server.
- Change ACPAgent in the same order as the API change: if a `StdioServerProcess.init` signature changes, tell the ACPAgent session first (ACPAgent CI uses Multitool main), or keep the new parameter with a value that ACPAgent can give.
