    ### Discoveries during the implementation

    - `MCPCapability` is a value: `init(server:)` awaits `waitUntilReady()`, reads `server.catalog` one time, takes `catalog.identity.name` as the noun and maps each `MCPCatalogEntry` to an `MCPTool(entry:server:)`. The `tools` property must be spelled `[any FoundationModels.Tool]`: the file imports `MCP` too, and a bare `Tool` is ambiguous between the two modules.
    - `withMCP(servers:)` is `async throws` and loops `withCapability(try await MCPCapability(server:))`. The `MultiToolBuilderError` doc said `withShell` was the one throwing registration method; it now names both.
    - The duplicate-noun case needs no new code. `withFiles(root:)` beside a server named `files` throws `.duplicateNoun` with name `files` at `buildRegistry()`.
    - `waitUntilReady()` suspends for ever on a server that was never connected (`.connecting`). The "never reaches `.ready`" case therefore connects and then calls `disconnect()`, so the state is `.disconnected` and `withMCP` throws `MCPServerError.notReady`.
    - The run-plane stamp of an MCP verb is readable from `MCPServer.inFlightCalls[...].context?.op` (`@testable`): `MCPServer.call(name:arguments:)` captures the ambient `ToolContext` into the in-flight record. The verb is synchronous, so the test runs the snippet in a `Task` and polls the in-flight table with `TestPoll` while a progress-reporting tool holds the call open. The registration-derived op is also pinned on `entry.journalOp` of the surface.
    - The generic sample generator gives a correct example for a converted schema: `await tools.loopback.echo({ text: "text" })`. It passes `TypedMockDryRun` for every loopback verb, and it runs for real against the server. No change to `SampleSnippet.swift` was needed.
    - The rendered `@returns` line of an `MCPTool` is `Promise<string>` with no trailing description: `MCPTool.Output` is `String`, and the renderer adds the " — plain text result." tail only for a tool that declares one. The golden `Goldens/MCPSurface.ts.txt` pins that shape.
    - `MCPCapabilityTests` is `.serialized`, as `LoopbackHTTPServerTests` is: each `.http` case holds a live SSE stream through `URLSession`, and several at once stall a server message under the full parallel run.
    - Shared helper: `MCPTestSupport.connectedLoopbackMCPServer(over:name:)` builds a scripted server with `addLoopbackTools()` and connects an `MCPServer` over either transport. `RegisteredJournalOpTests` and `BuilderSurfaceTests` use the helpers that were there.
    - `README.md` had no shell or files example. A new section "Capabilities: shell, files and MCP servers" shows the three short forms in one builder chain, with the `withMCP` contract under it.

## What
Make the MCP capability and its Builder short form. eventplan.md § "The capability contract": "The modules are opt-in: `withShell()`, `withFiles()`, and `withMCP(servers:)`." And § "Consolidation of the siblings": "Each connected server registers as its own top-level group: `tools.github.createIssue`, never `tools.mcp.github.createIssue`. The model must not see the transport."

- Modify `Sources/FoundationModelsMultitool/Capabilities/MCP/MCPCapability.swift` (the header exists from the first task): `public struct MCPCapability: Capability`. `noun` is the server's `ServerIdentity.name`. `tools` is one `MCPTool` per `MCPCatalogEntry` of the server's current catalog. `init(server: MCPServer) async throws` awaits `waitUntilReady()` and reads the catalog. One capability per server; `withMCP(servers:)` makes one for each.
- Modify `Sources/FoundationModelsMultitool/Surface/MultiToolBuilder.swift`: add `public func withMCP(servers: [MCPServer]) async throws -> Self`, next to `withShell` and `withFiles`, with the same doc comment style. It calls `withCapability(MCPCapability(server:))` for each server, in order. eventplan.md: "Servers connect before `buildRegistry()`." The method awaits readiness; it does not connect. A server that never reaches `.ready` throws `MCPServerError.notReady`.
- The duplicate-noun rule needs no new code: `withCapability` claims the noun, and `buildRegistry()` raises `MultiToolBuilderError.Kind.duplicateNoun`. eventplan.md: "An MCP server with the name `files`, against the files capability, fails loudly at `buildRegistry()`." Add the test.
- **The journal `op`.** eventplan.md § "Registration of capabilities": "`OperationEvent.op` stays the canonical `"verb noun"` string. Registration derives it as `"\(verb) \(noun)"`." Registration already does this for shell (`RegisteredJournalOpTests.swift` pins phase 2). Pin it for an MCP verb.
- Each entry of `findAPIs` needs a sample snippet (`Discovery/SampleSnippet.swift`). Check that the generic sample generator gives a correct call for a converted schema; if a case renders wrong, correct the generator, not the entry.
- Update `README.md` with a `withMCP` example next to the shell and files examples.
