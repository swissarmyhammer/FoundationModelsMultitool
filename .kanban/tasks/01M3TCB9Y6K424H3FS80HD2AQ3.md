title: Make the timed test scenarios safe under machine load
---
## What
Some unit tests race a wall clock. Under a high load average (55 to 170) the full `swift test` run fails some of them, and the failure set changes from run to run. Card ^vg37780 saw this (3 runs, no code change: 9 failing tests, then 2, then 0).

- `Tests/Support/MCPTestServer/DynamicToolsetScenario.swift`: `startDynamicToolsetScenario()` fires its stages on 1.5 s timers (`scheduleMutation(after:)`). A test that reads the "first" catalog after more than 1.5 s sees the stage-1 tool. Affected: `ServerModeTests` ".dynamic registers the initial re-schemad tool up front", `RegistryRebuildTests` "rebuildRegistry() after the scenario adds a tool...", `SurfaceRefresherTests` (add and remove tests), `LiveCatalogTests.dynamicToolsetScenarioEmitsOneSnapshotPerStage`.
- `ShellRunnerTests`: canceler tests poll `ps` for the spawned tree within `treeStartDeadline`; the time-limit test asserts `elapsed < timeoutUpperBound`.
- `ProviderFallbackTests` "a timeout skips the provider with one note" and `ResilienceTests.freshOperationWaitsForInFlightDisconnectStragglerBoundedByDisconnectGracePeriod`.

## Approach
Let the test drive each stage with an explicit trigger (or an injected clock) in place of a wall-clock timer. Do not widen deadlines. Do not add retries.

## Acceptance Criteria
- [x] No listed test depends on a wall-clock race to pass.
- [x] The listed suites pass under a high load average.
