## Problem

Task ^bt90anx found it. With tree-sitter-fortran 0.6.0, the Rust crate `swissarmyhammer-sem` reads no Fortran entity. Thus a diff of a `.f90` file has no change row, and `files` is 0.

The Fortran grammar keeps the name of a `function`, a `subroutine`, and a `module` in a child node (`function_statement`, `subroutine_statement`, `module_statement`). That child has the `name` field. The entity node itself has no `name` field, and its first named child is not an identifier. Thus `extract_name` in `entity_extractor.rs` gives `None`, and the walk records no entity. The kind `type_declaration` of `FORTRAN_CONFIG` is not a node kind of this grammar (a derived type is `derived_type_definition`).

The Swift port does the same, on purpose: the goldens in `Tests/FoundationModelsMultitoolTests/GitSemanticGoldens/fortran/` pin the Rust result (no change for each case).

## Decision necessary

The port follows the Rust crate (git.md decision 6). A correction in the Swift port only makes the two crates different. Thus the user must decide:

1. Correct the Rust crate first (for example read the `name` field of the `*_statement` child), then port the same correction and make the Fortran goldens again with the real Rust code.
2. Or keep the current result in both crates.

`../swissarmyhammer/crates/swissarmyhammer-sem/src/parser/plugins/code/definitions.rs` already reads the Fortran header (`function_header`) for the `code_context` tool. That reader can show the correct way.

## Acceptance

- The user records the decision on this task.
- When the decision is 1: the Rust crate and the Swift port read each Fortran function, subroutine, and module, and the Fortran goldens show the changes. #git
