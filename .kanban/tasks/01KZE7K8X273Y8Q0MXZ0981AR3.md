Discovered while measuring the phase-1 improvement pass on task `tkrdwb8` (2026-08-07). Not fixed there: changing a gated assertion mid-measurement would have invalidated the arms being compared, and this is a real change to what the suite gates on, which deserves its own decision.

## What

`ScenarioRunner`'s `grounded` check asserts `!NativeTranscript.invokedToolPaths(in: transcript).isEmpty`. `invokedToolPaths` is documented as, and is, a **lexical scan of each `runCode` call's `code` argument** for `tools.<name>(` call sites — it reads the source the model wrote, not what actually executed. So a snippet that calls only functions which do not exist still counts as "grounded".

Recorded instance, gated run B1 of the improvement pass:

```
SCENARIO [composeChain] result=PASS validAnswer=pass grounded=pass
RESULT [composeChain] toolCalls=2 invoked=["getTrip", "getWeather"] findAPIsFirst=false
  reply="The warmest city on your trip right now is **San Francisco** at 22°C (72°F)."
```

`getTrip` and `getWeather` exist in no fixture, so both calls threw. The fixture temperature is 31°C and the reply says 22°C — the answer is ungrounded in fact. It passed because `San Francisco` is a fixture city (so `validAnswer` held) and because two invented `tools.*` call sites were present in the snippet text (so `grounded` held). Both gates were satisfied by a run that never successfully called a tool.

This is a **false pass**, and by the intent statement recorded on `tkrdwb8` ("a green achieved through harness-side tuning is a FALSE PASS and worse than a red") that is the thing this suite most needs not to do. It is pre-existing — it is not caused by any change in that pass — and it cuts in the direction of the suite being *too lenient*, so fixing it can only lower measured pass rates.

## Approach

Ground the check in calls that actually returned, not in call sites that were typed. Options to weigh:

- Count only `tools.*` paths that exist in the registry surface — a lexical scan intersected with the real catalog. Cheap, no new plumbing, and it exactly separates this case.
- Read the `runCode` tool *outputs* rather than its arguments: a call whose rendered output is `ResultRenderer`'s repairable-error text did not ground anything.

The second is the truer signal. The first is a strict improvement available immediately. Decide with the evidence, and do not weaken anything else while in there.
