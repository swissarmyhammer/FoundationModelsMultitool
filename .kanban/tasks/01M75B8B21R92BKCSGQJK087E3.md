title: FileWalker lists files with libgit2, not with a git child process

## What
Request from testudoapp-75 (high priority). The rule of the user: no git command line anywhere; use libgit2 in the process.

`Sources/FoundationModelsMultitool/Capabilities/Files/FileWalker.swift:147` runs `/usr/bin/env git ls-files --cached --others --exclude-standard -z` as a child process. In the App Sandbox the `/usr/bin/git` shim refuses ("xcrun: error: cannot be used within an App Sandbox"). A Mac with no developer tools has no git. Thus the files listing (glob, grep) breaks in Testudo.

Change:
- Add `Sources/FoundationModelsMultitool/Capabilities/Git/LibGit2/LibGit2ListedFiles.swift`: a `LibGit2Repository` extension that gives the index entries plus the untracked files that the ignore rules do not exclude (with `GIT_STATUS_OPT_INCLUDE_UNTRACKED | GIT_STATUS_OPT_RECURSE_UNTRACKED_DIRS`), as paths relative to the work folder.
- `FileWalker.gitListedFiles(in:)` opens the repository with `LibGit2Repository(discoveringFrom:)`, keeps the paths below the walk root, and makes them relative to the walk root. The result is the same as `git ls-files` today. A folder outside git, or a bare repository, gives `nil`, thus the plain walk is the fallback, as today.
- Remove `listedFiles(byRunning:arguments:in:)`, `environmentProgramPath`, `gitListingArguments`, and the `Subprocess` import of FileWalker.
- Tests: replace each git command line in the tests (`TestSupport.runGit`: `init`, `add .`, `tag`, and the use in LibGit2CommitDetailTests) with libgit2 helpers in Tests/Support/MultitoolTestSupport. Remove `TestSupport.runGit`.

- [x] `Sources/FoundationModelsMultitool/Capabilities/Files/FileWalker.swift:153` `swift/error-handling` — `try? repository.listedFiles()` discards the error. When libgit2 cannot read the index or the status, the function returns nil and the caller silently falls back to a plain walk. The reason is lost, and an unexpected read failure is never reported. The fallback is still right, but the failure should be visible to a developer. Keep the fallback. Replace the `try?` with a `do { ... } catch { ... }` that logs the `LibGit2Error` before it returns nil, for example `logger.error("libgit2 listing failed; a plain walk stands: \(error)")`. Or make `gitListedFiles` `throws` and have `collectFiles` decide the fallback and log it.
- [x] `Sources/FoundationModelsMultitool/Capabilities/Files/FileWalker.swift:157` `completeness/invariant-propagation` — The git-listed path returns every index entry and every untracked path, but `enumeratedRegularFiles` returns only regular files. The two enumerations do not give the same kind of entry. An index entry that is a directory (for example a submodule gitlink) or a file the work folder no longer holds passes through `gitListedFiles` as a candidate. Glob and grep then receive a path that the plain walk would never return, so behaviour changes with the presence of a repository. The doc comment on `enumeratedRegularFiles` claims the two results are directly comparable, and that claim does not hold for this path. Filter the git-listed paths to regular files, as the plain walk does, or document and test the intended behaviour for gitlinks and for index entries the work folder no longer holds. Add one test with a submodule or directory index entry that pins which result is wanted.

Extract one shared helper in the LibGit2 layer that opens the index with LibGit2.makeHandle, frees it with defer, and runs a body on it. Call that helper from indexPaths in this change. Report the migration of LibGit2Blame.swift isInIndex to the same helper as a separate task, because that counterpart is outside this change.
