## Wait first
This task needs EXTRAS-12: the public mode type `ToolMode` (`open`, `sandboxed`) and the shared check that refuses `open` in a process in the App Sandbox, in the core `FoundationModelsExtras` target. The Extras session (foundationmodelsextras-de) builds it. Check `../FoundationModelsExtras` origin/main for `ToolMode` yourself. Multitool already depends on FoundationModelsExtras (`extrasDependencyName` in `Package.swift`). When EXTRAS-12 is on origin/main, remove the `blocked-external` tag. If the names of EXTRAS-12 are different, use its names.

## What
D128 (d), MT-15. The host sets the mode one time when it makes the registry.

- `Sources/FoundationModelsMultitool/Surface/MultiToolBuilder.swift`: `MultiTool.Builder` takes a `mode: ToolMode` (an init parameter, no default, so each host states it; change each caller in the tests and the IntegrationTests in the same change).
- `buildRegistry()` (and `build()`, which uses it) calls the shared EXTRAS-12 check first. In a sandboxed process, `open` mode throws at composition time, not at the first tool call.
- In `sandboxed` mode, `buildRegistry()` throws a new error, `MultiTool.Builder.BuildError.notAvailable(capability: "shell", mode: .sandboxed)` (use the existing error type of `buildRegistry` if there is one), when the builder has a `withShell` capability. A loud error is better than a silent skip: a host that calls `withShell` in `sandboxed` mode has a bug. The model never sees the shell.
- Files, git, snapshots, web, environment, sessions and operation tools register in both modes, as now.
- The verb alias tier of `MultiTool+ForgivingBindings.swift` (the `shellVerbs` list near line 298, for example `terminal.runCommand` and `bash.run`) must not route to the shell in `sandboxed` mode, because there is no shell noun. Confirm that the alias tier gives the normal "no such verb" answer.
- The description of `runCode` and of the tools does not name the shell in `sandboxed` mode.

The stdio MCP servers are a different task.
