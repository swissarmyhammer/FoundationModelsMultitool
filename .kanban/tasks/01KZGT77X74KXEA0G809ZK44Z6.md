    ### Validate the API calls statically, not just syntax + path existence (human, 2026-08-08)

    > "it would be even more clever if we're able to come up with a way to determine if the actual api calls are valid without actually calling them"

    **Mechanism: dry-run the sample against typed stubs.** Not a real execution and not a parser — install a stub for every `tools.*` path instead of the real tool, then run the snippet in the sandbox.

    Each stub:
    1. **Checks arity and argument types** against that tool's `@Generable` argument schema — the same schema `ToolAPIRenderer` already renders into the `declare function` block, so the check and the advertised signature cannot drift.
    2. **Returns a synthetic value shaped by the declared return type** — `{ tempC: 0, summary: "" }` for `Promise<{tempC: number, summary: string}>`, a 1–2 element array where an array is declared.
    3. **Wraps that value in a `Proxy` that throws on unknown property access**, so reading a field the return type does not declare is an error rather than `undefined`.
    4. **Records the call**, so we also learn which paths the sample actually reaches versus merely mentions.

    No real tool runs, so there are no side effects and no real data — `confirmBooking` never fires. That is exactly the "without actually calling them" property.

    #### What this catches that syntax + path checking does not

    | defect | caught by | present in our corpus? |
    |---|---|---|
    | unknown `tools.*` path | path check (already planned) | yes, `getTripCities`, `getCurrentWeather`, `getBooking` |
    | wrong arity | stub arity check | — |
    | wrong argument type | stub schema check | yes — `getWeather` throwing `.ambiguousCity` on a bad argument |
    | unknown field on a return | `Proxy` trap | **yes — `tripSnippetThatSkipsCitiesFails`: `getTrip` returns an object, model treats it as the city array** |
    | forgotten `await` | the existing pending-result proxy trap | **yes — `pendingResultPropertyAccessErrorRendersWithRepairInstruction` exists because models forget it** |
    | wrong destructuring | `Proxy` trap | yes |

    Two of those traps already exist in the interpreter. This reuses them rather than building new ones.

    #### Honest limits — state them in the code, do not oversell the check

    - **Logic errors are not caught.** A snippet that calls everything correctly and computes the wrong thing passes. Synthetic values are not real data, so any comparison, sort, or `if` branches arbitrarily.
    - **Branch coverage is arbitrary.** `if (cities.length > 2)` takes whichever path the synthetic array's length happens to produce. A sample can pass the dry run and still fail on real data.
    - **Synthetic value shaping needs care.** Arrays want 1–2 elements so `map`/`filter`/`[0]` behave; empty arrays make a snippet look fine while exercising nothing.
    - The dry run answers **"would this snippet throw on its API usage"**, not **"is this snippet correct."** Name the method for what it does.

    #### Ordering in the gate

    Cheapest and most certain first, so a failure feeds back the most specific message available:

    ```
    extract fenced block  → no fence         → feed back
    JSCheckScriptSyntax   → syntax error     → feed back verbatim
    path check            → unknown path     → feed back, naming the real paths
    dry run vs stubs      → thrown error     → feed back the thrown message
    ```

    Every failure kind still feeds the same generation session as its next turn, and exhausting retries still returns signatures alone.

    #### Deliberately out of scope for this card

    Exposing the dry run to the **main** model as a `checkCode`-style capability, so it can validate its own snippet before running it. That is a plausible follow-up and a different card — this one is about what `findAPIs` returns.

    ### The mocks must be type-aware, and the Proxy must not trip on JS protocol access (human, 2026-08-08)

    > "it'll need to be a bit smarter -- checking the parameter shapes too, but not getting stuck on the fact that the values are all proxy stubs. this is a kind of mocking."

    This is the part that decides whether the dry run helps or actively harms. A checker that produces **false failures** is worse than no checker: the bogus message feeds back into the generation session, and the generator "repairs" correct code into broken code.

    #### Hazard 1 — a mock passed as an argument must satisfy its parameter type

    Correct snippets chain calls, so mocks become arguments:

    ```js
    const trip = await tools.getTrip();
    const w = await tools.getWeather(trip.cities[0]);   // the argument IS a mock
    ```

    A naive check ("is this a `string`?") rejects that. **Rule: a mock standing for type `T` satisfies a parameter declared `T`.**

    Implementation that mostly sidesteps the problem: **make scalar mocks real values of the right type.** A `string` field mocks as `""`, `number` as `0`, `boolean` as `false`. Those type-check natively with no tagging and no special case. Only objects and arrays need a `Proxy`, because only they need unknown-field trapping — and those carry a hidden type tag the checker reads.

    So parameter-shape checking becomes: for an object parameter, are the required fields present, and does each field's value (or its tag) match the declared type, recursively. Missing required field → real failure. Extra property → not a failure.

    #### Hazard 2 — the Proxy must allow JS protocol access through

    If `get` throws on every unrecognised key, ordinary correct code fails:

    | access | triggered by | consequence if it throws |
    |---|---|---|
    | `then` | `await` on the value | every awaited mock fails |
    | `Symbol.toPrimitive`, `valueOf`, `toString` | string/number coercion, template literals | any interpolation fails |
    | `Symbol.iterator` | spread, `for…of`, destructuring an array | every array destructure fails |
    | `toJSON` | `JSON.stringify` | any serialisation fails |
    | `length` | array/string length | every `.length` read fails |
    | `constructor`, `Symbol.toStringTag`, `inspect` | engine internals, logging | arbitrary failures |

    **Rule: throw only on a key that looks like a data field the declared type does not have.** Allow every symbol key, every JS protocol name, and anything on `Object.prototype`/`Array.prototype` straight through. When in doubt, allow — a missed defect costs a chance to catch something, a false failure costs correct code.

    #### What this makes the dry run

    A **typed mocking layer**, not a type checker. State that in the naming and the docs. It answers: *given calls with correctly-shaped arguments and correctly-shaped returns, would this snippet throw?*

    Real failures it reports:
    - unknown `tools.*` path
    - wrong arity
    - argument whose type or required fields do not match the declared parameter
    - read of a field the declared return type does not have
    - forgotten `await` (the existing pending-result trap)

    Non-failures it must stay silent about:
    - a mock used where its declared type is expected, at any depth
    - any JS protocol or prototype access
    - extra properties on an argument object
    - whatever branch the synthetic values happen to select

    #### Test this the hard way

    Unit-test the **false-failure** direction as deliberately as the true-failure direction, because a false failure is the mode that corrupts the generation loop. At minimum, snippets that must pass clean:

    - chained call where one tool's return field is the next tool's argument
    - `await` on every mock
    - template-literal interpolation of a mock scalar
    - array destructuring and spread of a mocked array
    - `JSON.stringify` of a mocked object
    - `.length`, `.map`, `.filter` on a mocked array
    - an object argument carrying extra properties beyond the declared ones

    And snippets that must fail, each with the specific message fed back:
    - unknown path · wrong arity · wrong argument type · missing required field · undeclared field read · missing `await`

    ### Implementation notes and decisions taken inside the card's constraints

    **Requirement 8 forced a renderer refactor, and it is the strongest form of the requirement.** The card asks that the arity/type checks read "the same `@Generable` argument schema that `ToolAPIRenderer` renders into the `declare function` block, so the check and the advertised signature cannot drift." `ToolDescriptor` carried no schema, and `FindAPIsTool` only ever sees `APISurface.Entry`, so the schema had to travel on the descriptor either way. Rather than add a *second* traversal of the decoded schema alongside `tsType`, `ToolAPIRenderer` now has **one** traversal that produces a structural `ToolValueShape`, and the TypeScript declaration is rendered *from that shape*. `ToolDescriptor.signature` carries it. So `declaration` and the checker are not two derivations that agree — they are one value and a rendering of it. `declarationIsRenderedFromTheSignature` asserts that identity. Every pre-existing `ToolAPIRendererTests`/golden-file assertion still passes unchanged, which is what proves the refactor was behaviour-preserving.

    **The dry run is a pure-JavaScript harness, not Swift host functions.** The alternative — installing the mocks as real `AsyncHostFunction`s — would inherit `JSCInterpreter`'s forgot-`await` proxy for free, but a Swift host function's return value crosses the seam as `InterpreterValue` and lands in the sandbox as plain JSON, so there is no way to hand back a `Proxy`. That would have cost the undeclared-field trap, which is the check the card cares most about (`tripSnippetThatSkipsCitiesFails`). The harness therefore restates the forgot-`await` trap in JavaScript; it is documented as a restatement and why.

    **No hidden-tag-only cases exist, but the tag is implemented anyway.** Structural checking alone would accept every mock passed where its own type is declared, because a mock materialises all of its declared fields. The hidden `__mockShape` tag is still there, checked before any structural comparison, per the human decision — it short-circuits the "a mock standing for `T` satisfies a parameter declared `T`, at any depth" rule instead of re-deriving it. `mockTypeTagIsNotEnumerable` is the assertion that it stays invisible: the snippet itself throws if the tag leaks into `Object.keys`, so a clean dry run is the proof.

    **`length` is in the Proxy's pass-through list even though that costs a detection.** Reading `.length` off a mocked *object* would otherwise be a catchable undeclared-field read, but the card's allow-list names `length` explicitly and the standing rule is "when in doubt, allow". `map`/`filter`/`slice` are reached through `Array.prototype` only for array mocks, so `trip.map(...)` on an object result still fails — which is the recorded mistake that matters.

    **A widened `any` mocks as `{}` and accepts any argument.** Considered skipping the dry run entirely for any surface containing a widened `any`; rejected as unnecessary, since a false failure degrades to today's behaviour (retry, then signatures alone) rather than corrupting anything permanently. The limit is stated in the doc comment.

    **Two things the gate does that the card did not spell out, both toward "never block discovery":**
    - A watchdog timeout in the dry run is reported as a failure, not as "no opinion". A sample that cannot finish against mocks that resolve instantly cannot finish against real tools, and returning `nil` there would hand the model a hanging snippet.
    - The whole synchronous gate (`checkSyntax` + the mocked run, both blocking) is dispatched off the cooperative pool through a continuation, the same treatment `MultiTool` gives the real `runCode` path. Called inline it would tie up a cooperative-pool thread for the whole check.

    **Gated wiring.** `Registry.makeSessionTools(librarian:sampleGenerator:)` gained a defaulted-`nil` second parameter, and the integration harness's `makeScenarioSurface` passes `fixture.profile.standard` — so the gated arm measures the nested same-model call on the slot the card chose. `CLIRunner` and every other caller omit it and are byte-identical.

Requirement 9 scopes the change to `nextStepFooter`, and the footer is in-band, which is where teaching lands anyway.

## What

`findAPIs` currently returns signatures and tells the model to go write a snippet. That handoff is where the recorded failures happen — announce-then-stop with `toolCalls=0`, one call then narration, invented paths. Nine prompt-surface interventions have failed to move it.

Instead: **`findAPIs` generates a candidate `runCode` snippet for the query, validates it deterministically, and returns it alongside the signatures.** The model's job collapses from "compose a snippet against these signatures" to "run or adapt this snippet."

This uses the Router architecture rather than the prompt surface. Precedent exists: `findAPIs`'s selection tier already makes a nested model call inside `call(arguments:)` via `SelectionConfig(model:)`, on the `flash` slot.

## Shape

```
findAPIs(query)
  └─ search → matched entries
  └─ sample generation session   (standard slot, NO tools mounted → cannot recurse)
       ├─ tailored short instructions, exact output envelope
       ├─ extract fenced block → no fence?         → feed back, retry
       ├─ JSCheckScriptSyntax  → syntax error?     → feed back verbatim, retry
       └─ path check vs matched set → unknown path? → feed back, naming the real paths
       ⇢ bounded retries (2 retries / 3 attempts), then give up
  └─ pass → signatures + validated sample
     fail → signatures alone
```

**Human decisions already made:**
- Generation runs on the **`standard` (main) slot**, not `flash` — sample quality matters more than cost. Accepted risks: nested call on the same MLX model instance mid-turn is untested (GPU contention / deadlock), and gated wall-clock may go from 3–5 min to 6–10 min per run.
- **Parse-check only. Never execute the sample.**
- The failed parse **feeds back into the same session** as its next turn — a repair loop, not one-shot-and-discard. This is the in-band-repair technique the code-mode survey identified as the strongest in the field (Cloudflare rewrites sandbox errors to name the real globals; smolagents' parser hands back the literal fix), applied to the generator instead of the main model.

## Requirements

1. **New parse-only capability.** `Interpreter` has only `run`. Add a syntax-check method backed by `JSCheckScriptSyntax`, installing no host functions and executing nothing.
2. **Promote `UnknownToolHint.referencedToolPaths(in:)`** from `private static` — it is exactly the validator for "does the sample only name real paths", and it already backs the unknown-path hint.
3. **Deterministic extraction.** The generator's instructions demand exactly one fenced code block and nothing else. Absence of a fence is a failure that feeds back, so a chatty preamble cannot silently corrupt extraction.
4. **Three distinct feedback messages**, one per failure kind: no fence, syntax error (JSC's message verbatim), unknown `tools.*` path (naming the real paths).
5. **Never block discovery.** Generator error, timeout, or exhausted retries → return the signatures exactly as today. Never return an unvalidated sample.
6. **No recursion.** The generation session mounts no tools.
7. **Opt-in / injectable**, like the selection tier — a host that supplies no generator gets today's behavior, and tests can drive a scripted generator.
