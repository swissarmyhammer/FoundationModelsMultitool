Created by `^n6kgckr`'s gated run, which passed while proving less than its name claimed.

## What is missing

`RespondDrainTests` asserts `parked=0` when `respond(to:)` returns. That is necessary but **not sufficient**, because two different mechanisms empty the run plane:

1. the model collects its own backgrounded run in-band, because the pending envelope instructs it to (`PendingRunEnvelope.renderedMidfix`: *"Call this tool again with a snippet that does: return await wait(...)"*);
2. the turn ends with runs still parked, and Router's drain settles them and runs a continuation turn.

Measured on real hardware, **(1)** is what happens: `waitCalls` was 1 and 2 across two runs, `parked` 0 both times. So the existing scenario exercises the blocking surface and leaves Router's drain — the thing `^n6kgckr` exists to verify — completely untouched.

## What this card is

A scenario where the model **cannot** collect, so the drain is the only thing that can.

The shape: a snippet that starts long-running work and returns without awaiting it, so the turn ends while the run is genuinely in flight. Something like a fixture tool that sleeps well past the turn, invoked as `tools.slowThing({}); return "started";` — fired, not awaited.

Then assert what only the drain can produce:

- `respond` does not return until that run has settled;
- the settled result reaches the model, so the final answer is grounded in it;
- the run plane is empty on return, with the run's terminal event recorded rather than cancelled.

## Why this is worth doing rather than assuming

Router's drain is real code with a real design — whole-plane snapshot, bounded re-entry at four continuation turns (`RoutedSessionActor.parkedRunDrainRoundLimit`), a run parked from inside a drained turn drained too. None of that has ever executed in one of our scenarios. A bounded-re-entry loop that is never entered is a loop nobody has run.

It also guards a specific regression: if the drain broke tomorrow, every existing gated test would still pass, because the model's own `wait` calls would keep the run plane clean.

## Notes for whoever writes it

- Keep it inside the four-continuation-turn budget; a scenario needing more fails for a reason that is not a drain defect.
- Do not cancel anything. A cancelled turn is never drained — its parked runs stay parked, because ending them is `close()`'s job — so a cancelling scenario asserts about `close()` instead.
- The existing `runRespondDrainScenario` is the wrong shape to extend: it runs the same prompt through both surfaces for parity. This one wants a single surface and a different assertion set.
- `ScenarioCallLog.parkedRuns()` already reads the run plane through the ambient `ToolContext`, which is how "nothing survives" is observed today.

## Acceptance Criteria

- [ ] A gated scenario ends its turn with a run genuinely in flight, proven by the run being parked at the moment the model's answer is produced
- [ ] `respond` returns only after that run settles, and the answer is grounded in what it returned
- [ ] The run's terminal event is `succeeded`, not `cancelled` — the drain settled it rather than swept it
- [ ] The scenario fails if Router's drain is removed; state on the card how that was confirmed
