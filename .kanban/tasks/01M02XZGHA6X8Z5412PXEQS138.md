    ### Research — how the drain can be isolated at all

    Read the product code the card is about, and the answer is narrower than the card's sketch suggests.

    **Every `runCode` call parks, immediately.** `MultiTool.detachmentClocks(from:)` answers `waitSeconds = 0` for every call (`^cv98vff`), so a run is parked from the instant the model calls `runCode` until the snippet settles. The card's "fire, do not await" snippet is therefore not what creates the parked run — the run is parked whatever the snippet does. What the snippet controls is only *when it settles*: `JSCInterpreter.pumpUntilSettled` runs until the promise registry is empty, so a fired-and-forgotten `tools.slowThing({})` does keep the run alive past `return "started"` — but the run's return value is then `"started"`, and the slow tool's value never reaches the model at all. That shape cannot satisfy "the answer is grounded in what it returned".

    **There is exactly one in-band collector: the `wait` tool.** A second `runCode` snippet calling the sandbox globals cannot collect anything, because that `runCode` call parks immediately too — the model would need to wait on *its* token, and so on without end. `WaitTool.detachmentClocks(from:)` answers unbounded on both clocks, so `wait` never parks itself and, called with no `timeout`, blocks until the run settles. So `waitCalls == 0` is a complete proof that the model did not collect in band.

    **Therefore the assertion that isolates the drain is `waitCalls == 0` beside a grounded answer.** The fixture value reaches the model only through a collected terminal event; the model collected nothing; `RoutedSessionActor.settleParkedRuns` runs a continuation turn only when the plane was non-empty *after* the first turn's answer. So a grounded answer with zero `wait` calls can only have come from the drain.

    **The timing had to be made deterministic, not hoped for.** If the run settles before the first turn ends, the plane is empty at the drain's snapshot, no continuation turn runs, and the answer cannot carry the fixture value — a race, not a test. The fixture tool is therefore held on a gate that the scenario opens the moment it sees the first `SessionEvent.turnEnded` on `RoutedSession.streamSessionEvents()`. The run cannot leave the plane before the model's answer exists. That same instant is where the run-plane snapshot is taken, which is criterion 1 observed directly rather than deduced.

    The gate carries its own ceiling so a model that calls `wait` anyway fails honestly (on `waitCalls == 0`) instead of deadlocking: `wait` would hold the turn open, `turnEnded` would never arrive, and the gate would never open.

    **Router API used:** `RoutedSession.streamSessionEvents()` (turn-lifecycle events travel there whichever entry point ran the turn, `respond` included), `ToolContext.parkedRuns()`, and `ToolContext.wait(completionToken:seconds:)` — which returns a settled run's *retained* terminal event immediately (`SessionMailbox.settledTerminalEvents`), which is how the `succeeded`-not-`cancelled` criterion is read back.

    ### What actually happened

    The model got the **right answer** — manifest code `58204`, grounded in `rebuildArchive`. It just got it the wrong way: it called `wait` three times and collected the run itself. The gate held the fixture, but nothing stopped the model from parking on `wait` until the gate's own 90-second ceiling released the tool. That is why the run took 635 seconds.

    ### Why the design cannot work as specified

    The gate controls when the *fixture* may return. It cannot control whether the *model* calls `wait` — and the model will, because `PendingRunEnvelope` explicitly instructs it to: *"Call this tool again with a snippet that does: return await wait(...)"*. Holding the fixture longer just makes the model wait longer.

    So the loop is closed: **every `runCode` parks, every park hands back an envelope, and every envelope tells the model to collect.** On this product design a turn does not end with work in flight unless the model disobeys its own tooling.

    ### The larger question this raises, which is not this card's to settle

    If the envelope always instructs collection, then **Router's `respond` drain may never run for this host at all**. It is not dead code in Router — another consumer could leave a run parked — but for `FoundationModelsMultitool` as currently built, the in-band path appears to always win. That is worth knowing before anyone relies on the drain as a safety net.

    ### Where that leaves the work

    The scenario, the gate, the fixture and the ungated premise tests are all sound and committed (`2eab3f0`, `fdbf130`). What is missing is a way to make the model *not* collect. Options, none obviously right:

    1. Prompt the model not to wait — fragile, and the envelope contradicts it in-band, which is the exact fight `^2w9vbkm` already lost.
    2. A fixture whose run outlives the gated `.timeLimit` — turns a failure into a timeout, no better.

## What this card is

A scenario where the model **cannot** collect, so the drain is the only thing that can.

The shape: a snippet that starts long-running work and returns without awaiting it, so the turn ends while the run is genuinely in flight. Something like a fixture tool that sleeps well past the turn, invoked as `tools.slowThing({}); return "started";` — fired, not awaited.

Then assert what only the drain can produce:

- `respond` does not return until that run has settled;
- the settled result reaches the model, so the final answer is grounded in it;
- the run plane is empty on return, with the run's terminal event recorded rather than cancelled.

Router's drain is real code with a real design — whole-plane snapshot, bounded re-entry at four continuation turns (`RoutedSessionActor.parkedRunDrainRoundLimit`), a run parked from inside a drained turn drained too. It also guards a specific regression: if the drain broke tomorrow, every existing gated test would still pass, because the model's own `wait` calls would keep the run plane clean.
