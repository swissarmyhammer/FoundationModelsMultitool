title: 'Rename the background-run vocabulary: "parked"/"run plane" misdescribe work that is running'
---
This package invented "parked run" and "run plane" for **tool support that runs in the background and returns later**. Neither term is domain language, neither was asked for, and "parked" means *suspended* about work that is executing normally.

It is not only internal. It ships to the model, in the TypeScript the snippet author reads:

    Sources/FoundationModelsMultitool/MultiTool+SandboxGlobals.swift:166
    declare type ParkedRun = { state: "parked"; completionToken: string; tool: string;
                               op: string; kind: string; latestProgress: string | null };

In a package whose stated design rule is that the tool's own text carries the entire contract, a state name that misdescribes the state is a defect in the contract, not a matter of taste.

Counts in `Sources/`: `park` 57, `runPlane` 44, "run plane" 16.

## The deeper defect: one field, three vocabularies

`RunPlaneState` has six values, and they answer three different questions:

    parked           the run is going              <- about the RUN
    settled          the run finished              <- about the RUN
    deadlineElapsed  your wait() gave up; run still going   <- about YOUR WAIT CALL
    unknownToken     no such handle                <- about YOUR LOOKUP
    reported         your cancel() got an outcome  <- about YOUR CANCEL
    alreadySettled   your cancel() was too late    <- about YOUR CANCEL

A snippet branches on `state` without being able to tell whether it is being told *how the work is doing* or *how its own call went*. That conflation — not merely the word "parked" — is what makes this surface hard to reason about, and it confused this assistant repeatedly while working on `InBandCollectionCanaryTests`.

## The vocabulary to move to

**Run state** — what the background work is doing:

    running | complete | error

**What a `wait` returned** — the run state, plus two things that are not run states:

    timeout   the deadline passed; the run is still running
    unknown   no run under that handle

**What a `cancel` returned**:

    cancelled | complete   (the second meaning "too late, it had already finished")

Internal names follow the same plain reading: `ParkedRun` -> `BackgroundRun`, `RunPlaneState` -> `RunState`, `parkedRuns()` -> `runningJobs()`, "the run plane" -> "the background runs". `completionToken` and `wait` stay — they already say what they are, which is why they never confused anyone.

## `error` is a real contract change, not a rename

Today **there is no error state**. A failed run reports `settled` and puts the failure in a separate `outcome` field, so a snippet must read two fields to learn its work failed. Making `error` a first-class run state is the point of having a discriminator, but it changes what a snippet must branch on. It needs its own gated evidence, not a compile.

## Stage it by risk

1. **Internal names only.** Compile-checked, no model-facing string changes. Free.
2. **The `state` wire values.** Model-facing: the model matches on these strings, and `WaitTool` restates them (`h773bed` made `RunPlaneState` internal precisely so the two could not drift). Needs a gated run, not just a build.
3. **The `error` state.** Contract change per above. Separate gated evidence.

## Do not

- Do not rename Router's `elevation`/`ElevatingTool` vocabulary. That is their word for the seam and their repo; if it should change, it is a message to them, not a unilateral rename here.
- Do not fix the strings and leave the doc comments describing the old model. The comments carry the reasoning and are read more than the code.

## How the three vocabularies were separated

`state` is reserved for the run and carries `running` | `complete` | `error`. `result` is reserved for the caller's own call and carries `timeout` | `unknown` | `cancelled`. No object carries both, so a snippet still branches on one field and can no longer mistake "the run failed" for "my call gave up".

    status()  -> state, or result: "unknown" when the handle names no run
    wait()    -> state for a finished run; result: "timeout" | "unknown" otherwise
    cancel()  -> result: "cancelled"; state when it arrived too late; result: "unknown"

`error` is derived from the terminal event's own `OperationOutcome` rather than stamped by a call site, so no builder can label a failed run complete.

## What Router still owns

`ParkedRun` and `ToolContext.parkedRuns()` are `FoundationModelsRouter`'s public API, not this package's — the `ParkedRun` this card names at `MultiTool+SandboxGlobals.swift:166` is the TypeScript type, which is now `BackgroundRun`. Renaming Router's Swift type and `parkedRuns()` -> `runningJobs()` is a message to them, on the same terms this card sets for `elevation`. The gated-scenario harness is on card `^v6hfhdv`.
